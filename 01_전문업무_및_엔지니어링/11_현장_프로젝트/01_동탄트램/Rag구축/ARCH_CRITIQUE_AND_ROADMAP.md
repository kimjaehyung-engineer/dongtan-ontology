## 🚨 1. 현재 MVP 시스템의 4대 구조적 한계 (냉정한 비판)

### ① 단일 문서 1등만 선택하는 '외눈박이 라우팅' (Single-Doc Bottleneck)
* **코드 위치:** `server.py` 라인 3408 (`top_sc, target_doc_name, target_file_path, top_sec = scored_sections[0]`)
* **치명적 결함:** 스코어가 가장 높은 **단 1개의 문서만 선택**하여 Gemini에 넘김.
* **실패 시나리오:**  
  *"정거장 101번 지반 조건(지반보고서), 가시설 제원(구조계산서), 환승통로 이격기준(철도시방서)을 비교해줘"* 같은 실무 복합 질문 시, 1등인 지반보고서만 읽고 나머지 2권의 문서는 버려져 답변이 반쪽짜리로 전락함.

### ② 수작업 의존 인제스천 (No Automated Ingestion Pipeline)
* **현재 방식:** 새 PDF가 들어올 때마다 파이썬 스크립트(`enrich_all_meta.py`, 정규식 등)로 수동 키워드·섹션 작업 수행.
* **대용량 붕괴:** 보고서 50권, 도면 200장이 쏟아지는 실전 현장에서는 수기 전처리 유지보수가 불가능해지며, AI 소프트웨어가 아닌 "저마진 엑셀 노가다 대행업"으로 변질될 위험.

### ③ 플랫 JSON 파일 색인의 한계 (`_metadata_index.json`)
* **현재 방식:** 단일 JSON 파일을 파이썬 `for`문으로 훑으며 단순 문자열 매칭.
* **대용량 붕괴:** 문서가 100권, 섹션이 수천 개로 늘어나면 검색 지연(Latency) 급증 및 메모리 비효율 발생.
* **해결책:** SQLite FTS5(전문 검색 가상 테이블) 또는 하이브리드 검색 인덱스로 전환 필수.

### ④ 온톨로지 '거미줄(Hairball) 및 슈퍼노드' 폭발 위험
* **현재 상태:** 노드 20여 개로 데모에는 최적화됨.
* **대용량 붕괴:** 전 구간 부재, 시추공 100개, 계약 조항 500개 입력 시 노드가 10,000개로 급증. `차량기지`, `1공구` 같은 중심 노드에 수천 개 엣지가 물려 그래프 탐색 연산이 마비됨.
* **해결책:** 공구별/공종별 서브그래프(Sub-graph) 계층형 파티셔닝 필수.

## 👥 2. 대용량 확장을 위한 '차세대 에이전트 팀(v2)' 아키텍처

```
[사용자 복합 질문]
        │
        ▼
[1. 지휘관 에이전트 (Query Planner)] ── 질문 분해 (지반/구조/계약)
        │
        ├──────────────────────┬──────────────────────┐
        ▼                      ▼                      ▼
[2-A. 지반·지하수 에이전트] [2-B. 구조·가시설 에이전트] [2-C. 시방·계약 에이전트]
(시추공 SQL + 지반보고서)   (구조계산서 + 단면도)     (입찰안내서 + KCS/KDS)
        │                      │                      │
        └──────────────────────┼──────────────────────┘
                               ▼
        [3. 검증관 에이전트 (Discrepancy Checker)]
        - 도서 간 수치 불일치(Clash) 감지 (예: phi=30° vs phi=32°)
                               ▼
        [4. 편집장 에이전트 (Synthesizer)]
        - 최종 팩트 종합 표(Table) 및 원본 페이지(p.XX) 링크 조립
                               ▼
                        [최종 완성 보고서]
```

### 각 에이전트의 구체적 임무
1. **[지휘관] 쿼리 플래너 & 오케스트레이터:**  
   복합 질문을 하위 태스크로 분해하여 해당 전문 에이전트들에게 병렬 하달.
2. **[전문가] 분야별 3대 도메인 에이전트 (Parallel Fan-out):**  
   각자 자기 공종 문서만 핀포인트로 읽어 토큰 낭비 방지 및 속도 극대화.
3. **[검증관] 교차 검증 및 불일치(Clash) 감지 에이전트:**  
   지반보고서와 구조계산서 간 지반정수 차이, 시방서 기준 미달 여부를 크로스체크하여 경보 발령.
4. **[편집장] 종합 합성 에이전트 (Fan-in Synthesis):**  
   모든 분석 결과를 취합하여 결재용 실무 서식 및 마스터 체크리스트로 최종 변환.
